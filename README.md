# chishenme · 微信小程序工作区

两个自己写给自己家用的微信小程序，外加一份 Vibe Coding 的流程笔记。
都是原生小程序（没有用框架），一台手机、一个 AppID 就能跑起来。

| 目录 | 是什么 |
|---|---|
| `chishenme/` | **今天吃啥** — 家庭点菜。80 道内置菜（含两广特色菜）+ 自己拍照加菜、摇一摇配「三菜一汤」、家人共用一个房间实时同步 |
| `yimuzhang/` | **一目账** — 个人记账。明细 / 记一笔 / 统计 / 我的 四个 tab |
| `vibe-coding-SOP.html` | 五阶段流程与上线检查清单（写这两个项目时总结的） |
| `CHANGELOG.md` | 两个项目各自的版本历史 |
| `今天吃啥-*.md` `一目账-*.md` | 使用说明、部署清单、验收清单、开发计划 |
| `.workbuddy/verify/` | 自动化检查脚本，见下面「怎么验证」 |

## 首次运行

代码 clone 下来**不能直接跑**，缺两个故意没上传的文件（一个是云环境配置，
一个是开发者工具的个人设置，详见 `.gitignore` 里的说明）。补上这两步就行：

```bash
# 1. 云开发配置（不填就是本地模式，功能一样用，只是家人之间不同步）
cp chishenme/config.example.js chishenme/config.js

# 2. 开发者工具里打开项目，自己填 AppID
#    详情 → 基本信息 → AppID → 改成你自己的
```

用微信开发者工具分别「导入项目」，选 `chishenme/` 和 `yimuzhang/` 两个目录。

想开家庭共享（`chishenme`）的话，多花十分钟：顶部「云开发」→ 创建环境 →
把环境 ID 填进 `chishenme/config.js` 的 `CLOUD_ENV` → 建三个集合
`csm_families`、`csm_menus`、`csm_dishes`（都选
「所有用户可读，仅创建者可读写」）→ 右键 `cloudfunctions/csmMenu`
「上传并部署」。完整步骤见《今天吃啥-部署清单.md》。

## 怎么验证

改完代码跑这几个脚本，一共 **995 项**断言。不需要连云环境，
云函数那部分是用内存假数据库把真实的云函数代码跑一遍。

```bash
NODE=node
PY=python

# 一目账（合计 154 项）
$NODE .workbuddy/verify/core-test.js          # 114 项
$NODE .workbuddy/verify/wxml-check.js         #  32 项
$PY   .workbuddy/tools/check-icon-colors.py   #   8 项

# 今天吃啥（合计 841 项）
$NODE .workbuddy/verify/chishenme/core-test.js     # 399 项
$NODE .workbuddy/verify/chishenme/wxml-check.js    #  92 项
$NODE .workbuddy/verify/chishenme/cloud-test.js    # 330 项
$PY   .workbuddy/verify/chishenme/check-images.py  #  20 项
```

其中两个最值钱的：

- **`wxml-check.js`**（三方一致性）—— 小程序一个页面由 4 个文件组成，
  最容易出的错是「四件套对不上」：`bindtap` 写了但 JS 里没这个函数、
  模板里用了 `{{foo}}` 但 `data` 里没有、`class` 在 WXSS 里没定义。
  这些开发者工具都不报，只有点到那个按钮才发现。这个脚本静态全揪出来。
- **`cloud-test.js`**（云函数离线测试）—— 云函数里跑着这个项目唯一可信的那部分逻辑，
  却偏偏是最难验证的（要连真实云环境、要多个微信号）。这里用 `Module._load`
  拦截 `wx-server-sdk` 塞一个内存假库，跑的是**真实的云函数代码**。

> **检查脚本里不要写死菜道数。** 这几份脚本原来分别断言「35 道菜」「荤菜 12 道」
> 「320×320」，扩到 80 道时集体挂掉。当时改成断言**真正的不变量**
> ——「图片数 == 菜库数」「各分类相加 == 总数」—— 之后再加菜就一处都不用动了。
> 一个「改了检查才能过」的检查器，迟早会被顺手改成新数字然后彻底失去意义。

## 几条踩过坑才立下的规矩

代码里都留着注释，这里列最值得说的三条：

1. **金额一律用整数「分」存**，只用 `yuan2fen`/`fen2yuan` 转换。
   JS 里 `0.1 + 0.2 = 0.30000000000000004`，用浮点数记账迟早对不上账。

2. **云函数跑在 UTC**。日期一律 `Date.now() + 8h` 再取 UTC 字段，
   否则北京时间晚上 8 点以后点的菜会存成「明天」。

3. **微信 `<input>` 自带 `height:1.4rem`**。给它写了 `box-sizing:border-box`
   就必须同时写死 `height`，不然上下 padding 会把内容区挤成负值 ——
   **输入的文字整行被裁掉，而且只有真机才看得见**，模拟器和浏览器复刻都正常。

## 版本管理

一个仓库装两个小程序，所以**标签带项目前缀**，免得两个项目抢同一个 `v1.1.0`：

```bash
git tag -a chishenme-v1.2.0 -m "今天吃啥 v1.2：房主可解散房间"
git tag -a yimuzhang-v1.1.0 -m "一目账 v1.1：快捷金额 + 自绘 tabBar 图标"
git push --tags
```

版本号怎么排：**加功能进次版本，只修 bug 进修订号，改了数据结构且老数据要迁移才动主版本**。
标签打在 `main` 上，代表「当时整个仓库的完整状态」，不是某一次提交。
哪天想回头看某个版本，用 `git checkout chishenme-v1.1.0` 就能把整棵树退回去。
具体每一版改了什么，见 `CHANGELOG.md`。

日常改代码就三步：

```bash
git add -A
git commit -m "做了什么"     # 第一行写清楚「改了什么」，细节再另起一段
git push
```

两个约定：

- **一次提交只做一件事。** 上面那三个提交就是例子：功能、清理各一条，
  将来要回滚某一项时不用连坐。
- **发一个新版本时才打标签**，不必每次提交都打。
- **改了 `chishenme/cloudfunctions/` 就得重新部署云函数。**
  它不会跟着小程序代码一起上传 —— 漏了就是「界面是新的、云端是旧的」，
  手机上会弹「未知操作: xxx」。见《今天吃啥-部署清单.md》第 4 步。

## 菜图从哪来的

80 道菜的图不是同一种来源，这点得说清楚：

- **35 张**（初版）：AI 生成，竖版出图后居中裁方（把生成器右下角的水印裁掉）。
- **29 张**：来自**维基共享资源 / 中文维基百科**，CC 或公有领域授权，
  天然没有水印，可以合法使用。检索时只用文件名里真的含这道菜名的图
  （`intitle:`）—— 普通全文搜索会把「阳朔啤酒鱼」匹配到啤酒罐、
  把「恭城油茶」匹配到油茶**树**。
- **16 张**：上面两条都找不到合格图的地方特色菜，仍然用 AI 生成。

全部统一压成 **300×300 JPEG(q75)**。这个规格是被逼出来的：小程序主包上限
**2MB**，80 张按原来的 320×320/q82 要 1.81MB，贴死上限没有余量；
降到 300×300/q75 后约 1.42MB，主包落在 **1.60MB（占上限 80%）**。
菜卡在手机上显示宽度约 165px，300px 仍有富余，肉眼几乎看不出差别。

## 菜谱：内置的 80 道 + 自己加的

内置的 80 道写死在小程序包里（`data/dishes.js` + `images/dishes/`）。
**对家人是只读的，房主可以改、可以收起来**：

- **改**：菜名、分类、主料、要点，还能换一张自己的照片。改完**全家人都看到**——
  同一道菜在家里有两个名字是最难解释的状态。
- **收起来**（也就是「删」）：家人看不到也点不到。菜库底部会多出一行
  「已被你收起来的内置菜 N 道」，点开可以逐个恢复或全部恢复。
- 为什么是「收起」不是真删：数据和图都打在包里，**物理上删不掉** ——
  没法只删掉某一台手机上的那一份。所以删的语义是「对全家隐藏」，而且一定能恢复。
- 房主校验只在**服务端**（`fam.owner !== openid` → `NOT_OWNER`）。
  客户端那个「是房主才显示按钮」只是界面上的方便，改一行 wxml 就能绕过去。
- 判定房主这个动作本身，本地模式（没配云开发）返回 true —— 一台手机上的菜谱
  本来就只有自己看，那里「我」就是房主。

自己加的菜走的是另一条路：

- 入口在**菜库页右上角「＋ 加菜」**，以及**菜品详情弹层**里的「编辑 / 删除」
  （只有自己加的菜才出现这两个，删除还有一道二次确认）。
- 接了云开发 → 照片传到云存储、菜名存云数据库，**全家人都能看到、都能点**；
  没接云开发 → 只存本机，重启也不丢，但只有这台手机看得见。
- **只有加这道菜的人**能改它、删它。别人加的菜你一样能点、能收藏，只是改不了。
- 云模式删菜时，会**连这道菜在当日菜单里的记录、以及云存储里的那张图**一起清掉，
  顺序也是「先摘菜单 → 再删图 → 最后删菜」，不留孤儿数据。
- 菜库页顶部有个**搜索框**：输「鸡」能同时搜到内置的「宫保鸡丁」和你自己加的菜。
  匹配范围是**菜名 + 主料**，菜名命中的排在前面；点一下分类就退出搜索。
  ★ 匹配和排序规则放在 `data/dishes.js` 的 `search()` 里而不是页面里 ——
  这条规则写错了**不会报错**，只会「搜出来的顺序怪怪的」，放数据层才能被 core-test 守住。

照片是怎么送到手机上的（这里藏着一个很不显眼的坑）：

- 云开发有**两套互相独立的权限**：数据库的和云存储的。菜名存在数据库里、照片存在
  云存储里，**只改数据库权限对照片没有任何帮助**。
- 这个环境的云存储权限是「仅创建者及管理员可读写」，于是**家人读不到别人传的照片** ——
  客户端直接读会报 `STORAGE_EXCEED_AUTHORITY`，开发者工具里只留一行
  `Failed to load image .../cloud://...` + `net::OK`，一点都不像权限问题。
  而**免费版云开发不给改这个开关**，控制台会拦下来提示升级付费版。
- 所以绕过去：**由云函数去换链接**。云函数是管理员身份，安全规则只约束客户端、管不着它。
  `listDishes` 顺手把这次要返回的所有 `cloud://` 换成带签名的 `https://` 临时链接
  一起发下来（超过 50 个自动分批），前端**只在显示的那一刻替换**（`imageOf` 一处）。
- ★ 临时链接**绝不写进任何存储**。它默认 1 天过期，落库就是给自己埋一颗定时炸弹；
  本机缓存和云端记录里存的永远还是 `cloud://`。切回前台超过 6 小时自动重拉一次。
- 顺带解决一个隐患：安卓真机上有「`<image>` 渲染不了 `cloud://`」的反馈，
  现在交给渲染层的是普通 `https://` 地址，那条路也一起绕过去了。

实现上有一点值得记：内置菜、自己加的菜、房主对内置菜的改动**没有分成三套代码**，
而是在 `data/dishes.js` 里做了两层**运行时叠加** —— `byId` / `byCat` / `imageOf` /
`search` 自动把它们合起来。于是点菜页、菜单页、收藏页在老功能上**一行都没改**
（摇一摇只动了一处：第四道菜原来直接拿出厂数组，会摇出房主已经收起来的菜）。
要是让每个页面自己查两次，将来加一个新页面就会漏一处，而且漏了不会报任何错。

★ 叠加层有一条铁律：**绝不去改 `DISHES` 里的对象**。那份静态数据被 `D.TOTAL`、
图片规格检查、菜数断言一起指着，一旦被就地改掉，错误会静悄悄地扩散到整个工作区。
所以每个读取函数都是「没改过就返回原引用，改过就返回一个新对象」。

## 说明

个人自用项目，代码按现状提供，没做过多打磨。
`chishenme-raw/` 是菜品图的**原始大图**（80 道，约 84MB），
成品图处理在 `chishenme/images/dishes/`，重新出图跑
`.workbuddy/tools/process-dishes.py` 即可。

1024 完全够重新出图，而全尺寸存会把仓库白白撑大 30 多兆。
